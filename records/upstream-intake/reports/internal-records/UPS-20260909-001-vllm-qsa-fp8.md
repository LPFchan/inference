## Candidate Change

- Title: Store Qwen3.8 Flash-Next's main QSA K/V cache in FP8 E4M3
- Upstream area: Qwen4Exp NVIDIA sparse attention
- Upstream summary: current vLLM main contains the QSA kernel rewrites; PR #55557 adds FP8 main-cache storage and dequantization inside QSA.
- Exact upstream feature, provider, contract, or path: `vllm/models/qwen4_exp/nvidia/qsa.py` and `nvidia/ops/qsa.py`
- Exact local downstream surface affected: `docker/mangchi-vllm/`, `etc/mangchi-agent.json`, and the Thor Flash-Next runtime
- Why it matters: BF16 cache storage cannot provide the model's native 262,144-token context within the current safe memory budget.
- What this actually means in practice: K/V occupies eight bits in the cache, while QSA converts selected K rows to BF16 and V rows to FP16 for attention.
- Before: the live v0.29 image accepts only BF16 main QSA K/V and serves 131,072 context.
- After: the candidate image accepts FP8 E4M3 main QSA K/V and requests 262,144 context.
- Concrete consequence: the same cache memory should hold enough tokens for one native-length request.
- What is not changing: model weights remain NVFP4 and the SSD-backed BF16 PLE table remains mmap-backed. BF16 remains the model compute dtype; the hybrid GDN/Mamba recurrent cache is float32 at runtime.
- Expected end-user effect: Flash-Next accepts conversations up to its native 256K limit.
- Breaking or migration risk: medium; #55557 has SM120 and SM121 evidence but no SM110 result.
- Relevance to the fork's current stage: immediate, because Flash-Next is already serving on Mangchi.
- Evidence source category: upstream PRs, upstream code, local Docker patches, and live runtime measurements.

## Intake Analysis

- What user or operator problem does this change solve upstream? It cuts the largest context-dependent cache allocation roughly in half.
- What assumptions from upstream do not carry over cleanly to the fork? Upstream testing covers other Blackwell families; Mangchi is SM110 and also uses an SSD-backed PLE patch plus older aarch64 dependencies.
- Is the upstream change about policy, implementation, or both? Implementation only.
- Is this a duplicate or near-duplicate of an existing local change? No. The local image only bypasses an incompatible top-k kernel and mmap-loads PLE.
- If it overlaps an existing local implementation, whose implementation should win and why? Current upstream QSA should be the base; the local top-k and PLE adaptations remain only where SM110 and memory layout require them.
- What are the main upsides of introducing this change? Native context capacity and the accumulated QSA correctness/performance fixes on main.
- What are the main downsides, costs, or maintenance burdens? Pre-release source pin, SM110 testing, and possible FP8 quality or MTP-acceptance loss.
- Does this include security or hardening work that collides with, duplicates, or weakens an existing local implementation? No.
- What minute compatibility details matter if this lands? The QSA indexer moved to `ops/qsa_indexer.py`; the PLE constructor dropped compile-era arguments; the main cache uses per-tensor scales; the cooperative top-k SM110 exclusion still must apply.
- Literal user or operator scenario: the operator opens a conversation near 256K tokens and the request is admitted with Thor's allocation raised from 0.65 to 0.67.
